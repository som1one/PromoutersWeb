# Гайд по тестированию СУУПР по ТЗ

Документ описывает, как развернуть и проверить, что система покрывает требования полного ТЗ — все роли, маршруты, мастер-заявки, план расходов, выплаты, уведомления.

## 1. Подготовка среды

### 1.1. Backend

```powershell
# 1. Виртуальное окружение и зависимости
pip install -e .[dev]

# 2. Поднять PostgreSQL (если ещё не поднят)
docker compose up -d db

# 3. Файл окружения
copy .env.example .env
# Проверьте, что POSTGRES_HOST/POSTGRES_PORT соответствуют вашему контейнеру
# Для локального docker-compose: POSTGRES_PORT=5433 (как в текущем .env)

# 4. Применить миграции до head
python -m alembic upgrade head
# Должна показать: 0005_full_tz (head)

# 5. Заполнить демо-данными
python scripts/seed_demo_data.py
```

После seed в системе появятся следующие учётные записи (пароль у всех `demo12345`):

| Роль | Логин | Телефон |
|---|---|---|
| Собственник | `owner.demo` | `+79990000001` |
| Руководитель филиала (Центр) | `manager.center` | `+79990000002` |
| Директор по рекламе (Центр) | `director.center` | `+79990000003` |
| Промоутер (Центр) | `promoter.center` | `+79990000004` |
| Руководитель филиала (Север) | `manager.north` | `+79990000005` |
| Промоутер (Север) | `promoter.north` | `+79990000006` |
| Мастер (Центр) | `master.center` | `+79990000007` |

Логин в системе **по телефону**, не по username.

### 1.2. Запуск API

```powershell
uvicorn promouters.main:app --reload
```

API: `http://localhost:8000`
Swagger: `http://localhost:8000/docs`

### 1.3. Frontend

```powershell
cd frontend
npm install   # один раз
npm run dev
```

UI: `http://localhost:5173`

## 2. Автотесты

```powershell
# Полный прогон тестов
python -m pytest tests/ -v
```

Ожидаемо: **10 passed**.

Что покрыто автотестами:

- `test_smoke.py` — приложение поднимается, OpenAPI отдаётся, логин с плохим паролем отбивает 401.
- `test_master_requests.py` — полный жизненный цикл заявки мастеру (создание → принял → в пути с GPS → в работе с GPS → готово → забрал на СД), запрет перепрыгивания статусов, изоляция филиалов.
- `test_expense_plans.py` — план расходов: черновик → отправлен собственнику → согласован, ветка `needs_revision` возвращает в черновик, промоутеру создавать план запрещено.

## 3. Сценарии ручного тестирования по ТЗ

### 3.1. Авторизация и права доступа (раздел 4 ТЗ)

1. Откройте `http://localhost:5173/auth/login`.
2. Войдите как `+79990000001` / `demo12345` (собственник).
3. Проверьте, что в нижней навигации виден **«Аудит»** — это раздел собственника.
4. Откройте `/app/audit-logs` — там видны записи действий по всем филиалам.
5. Выйдите и войдите как промоутер `+79990000004`.
6. Проверьте, что попытка зайти на `/app/audit-logs` или `/app/admin/routes` редиректит обратно на свои разделы (`/app/routes`). RoleGuard работает.

### 3.2. Управление пользователями и филиалами (раздел 4.1, 4.2)

1. Залогиньтесь собственником.
2. Через Swagger `POST /api/v1/branches` создайте филиал.
3. После создания на странице `/app/notifications` у собственника должно появиться уведомление `Branch created`. Уведомление о действии собственника не уходит самому собственнику; чтобы это проверить, создайте филиал от руководителя филиала через `POST /api/v1/users` (или измените пользователя — собственник получит «User updated»).
4. Логин под `manager.center`. Через Swagger `POST /api/v1/users` создайте директора рекламы или промоутера в своём филиале.
5. После создания зайдите как `owner.demo` и убедитесь, что в `/app/notifications` есть запись `User created`. Это требование «уведомления собственнику о любых изменениях, особенно действий руководителя филиала».
6. Попытайтесь руководителем филиала Центр создать пользователя в филиале Север — API должно вернуть 403.

### 3.3. Создание маршрута и фото маршрута (раздел 4.3, 5.4)

1. Логин: `director.center`.
2. Откройте `/app/admin/routes` — увидите демо-маршруты.
3. Через Swagger `POST /api/v1/routes` создайте новый маршрут с минимум 2 точками (start + finish), укажите `payout_rate_id` (берите из `GET /api/v1/payout-rates`).
4. Через Swagger `POST /api/v1/routes/{id}/map-image` (multipart/form-data, поле `file`) прикрепите фото-карту маршрута. Это закрывает требование «создание маршрутов/карт для промоутеров (фото или описание маршрута)».
5. После прикрепления повторный `GET /api/v1/routes/{id}` вернёт `map_image_url` — публичная ссылка на загруженный файл через `/media/...`.
6. Назначьте маршрут промоутеру: `POST /api/v1/routes/{id}/assign` `{"promoter_id": "<uuid>"}`. У `promoter.center` появится уведомление «New route assigned», у собственника — «Route assigned».

### 3.4. Тип оплаты и ставки (раздел 4.3 — почасовая / за листовку)

1. От директора по рекламе `POST /api/v1/payout-rates`:
   ```json
   {
     "name": "Тест почасовая",
     "rate_type": "hourly",
     "amount": "150.00",
     "branch_id": "<id_филиала>",
     "is_active": true
   }
   ```
2. Аналогично создайте `per_leaflet`. Создание `fixed_shift` через Pydantic-валидацию запрещено — в MVP только два типа.
3. После создания у собственника придёт уведомление `New payout rate created`.

### 3.5. Сценарий промоутера: старт, GPS, фото, завершение (раздел 4.5, 5.4)

1. Логин: `promoter.center`.
2. На главной увидите назначенные маршруты. Откройте маршрут со статусом `assigned`.
3. Нажмите **«Начать»** — браузер запросит геолокацию, маршрут перейдёт в `in_progress`. Стартовая GPS-точка зафиксирована (`GeoPingSource.START`).
4. Перейдите на `/app/routes/<id>/execute`. Загрузите хотя бы одно фото с GPS — в `media/routes/<id>/<session>/` появится файл.
5. Дождитесь напоминания о фотоотчёте: фоновый планировщик (`services/reminders.py`) шлёт хаотичное уведомление каждые 15–30 минут. Для ускоренной проверки в `.env` можно временно поставить:
   ```
   PHOTO_REPORT_REMINDER_MIN_MINUTES=1
   PHOTO_REPORT_REMINDER_MAX_MINUTES=2
   ```
   и перезапустить uvicorn — напоминание появится в `/app/notifications` через 1–2 минуты после старта смены.
6. Завершите маршрут на странице `/app/routes/<id>/finish`: укажите количество листовок и краткую сводку. Сессия становится `completed`, фиксируется финальная GPS-точка (`GeoPingSource.FINISH`), автоматически рассчитывается выплата.
7. После завершения у руководителя филиала и собственника — уведомление `Route completed`.

### 3.6. Приём и передача отчёта промоутера (раздел 4.3 ТЗ)

1. Логин: `director.center`.
2. На завершённом маршруте `POST /api/v1/sessions/<session_id>/accept-report` `{"comment": "ОК"}` — отчёт переходит в `accepted_by_director`.
3. `POST /api/v1/sessions/<session_id>/forward-report` `{"comment": "Передаю руководителю"}` — переход в `forwarded_to_manager`. Руководителю филиала и собственнику уходят уведомления `Promoter report forwarded`.
4. Альтернативно `/reject-report` возвращает отчёт в `rejected`, чтобы директор мог отправить промоутера переделывать.

### 3.7. Кабинет мастера (раздел 4.4 ТЗ)

1. Логин: `master.center`.
2. В нижней навигации откройте «Заявки». В демо-данных уже есть три заявки разной зрелости.
3. На заявке в статусе `new` нажмите **«Принял»**. Статус меняется на `accepted`. Геопозиция пока выключена.
4. Нажмите **«В пути»** — браузер запросит геолокацию, статус становится `on_the_way`, `geo_tracking_enabled=true`, в `master_geo_pings` появляется запись.
5. Нажмите **«В работе»** — `in_progress`, ещё одна GPS-точка.
6. Нажмите **«Готово»** — `completed`, геопозиция выключается.
7. В развороте заявки откройте **«БСО / документы»**, в поле комментария напишите что-нибудь и выберите файл — он загрузится в `media/master_requests/<id>/`.
8. Финальный шаг — **«Забрал на СД»**, статус `handed_over`. Это терминальное состояние.
9. На каждом переходе в развороте «История статусов» появляется новая запись лога. Собственнику на каждое изменение приходит уведомление.
10. Попробуйте от мастера перепрыгнуть статусы — например, от `new` сразу к `in_progress`. API ответит `409 Conflict`.

### 3.8. План расходов и согласование (раздел 4.2, 5.5)

1. Логин: `manager.center`.
2. Откройте `/app/expense-plans` или `/app/income-expense`.
3. Заполните форму **«Новый план»**: название, период с/по, добавьте позиции (Аренда офиса, Листовки) — итог считается автоматически.
4. Нажмите **«Создать план»**. Появляется в списке со статусом `draft`.
5. Раскройте созданный план и нажмите **«Отправить собственнику»** — статус становится `submitted`. Собственнику приходит уведомление `Expense plan submitted`.
6. Логин: `owner.demo`. Откройте `/app/expense-plans` или `/app/income-expense`.
7. На плане в статусе `submitted` нажмите **«Согласовать»** — статус `approved`. Автору плана приходит уведомление `Expense plan approved`.
8. Кнопки **«На доработку»** и **«Отклонить»** проверяют ветки `needs_revision` (план возвращается в `draft`) и `rejected`.

### 3.9. Доход/Расход (раздел 5.5 ТЗ — «интеграция с разделом Доход/Расход»)

1. Логин: `owner.demo` или `manager.center`.
2. Откройте раздел **«Финансы»** в нижней навигации (`/app/income-expense`).
3. Видите три метрики: сумма выплат, сумма расходов, дельта.
4. В секции «Выплаты по промоутерам» нажмите **«Открыть детализацию»** на любом промоутере — появится список начислений с суммой, статусом, датой и привязкой к маршруту. Это и есть «детализация по каждому промоутеру», как требует ТЗ.
5. В секции «Расходы филиала» — список планов расходов со статусами.

### 3.10. Аудит (раздел 5.1 ТЗ)

1. Логин: `owner.demo`.
2. Откройте `/app/audit-logs`.
3. Должны быть видны записи: создание маршрутов, смена статусов, выплаты, мастер-заявки и т.д.
4. Также проверьте `GET /api/v1/audit-logs?action=master_request.status.in_progress` — фильтр по action работает.
5. Логин: `manager.center` → `/app/audit-logs` показывает записи только своего филиала. Это закрывает требование «ограничение доступа по филиалу».

### 3.11. Уведомления (раздел 5.6 ТЗ)

1. Логин любым пользователем.
2. Откройте `/app/notifications` — список уведомлений.
3. По цепочкам сценариев выше у каждой роли копится свой набор:
   - Промоутер: `New route assigned`, `Photo report reminder`.
   - Руководитель филиала: `Route completed`, `Promoter report forwarded`, `Expense plan approved/rejected`.
   - Собственник: всё перечисленное + `Branch created/updated/removed`, `User created/updated/removed`, `Route created/assigned/updated/completed`, `Master request *`, `Expense plan submitted`.

## 6. Известные ограничения

- Фотонапоминания считают «время с последнего фото» относительно `started_at` сессии, если фотоотчётов ещё не было — по сути напомнит сразу через минимальный интервал.
- В демо-seed у активной сессии ставится `started_at = now() - 1ч 20м`, поэтому при первом запуске seeder + reminder cycle промоутер быстрее увидит первое напоминание.
- Браузер просит разрешение на геолокацию — без него страницы выполнения маршрута и смены статуса мастера не получат координаты, но смогут продолжить работу (статусы поменяются, GPS не запишется).
- В UI кабинета мастера и плана расходов используется системный `<input type="file">` — без специальной стилизации. Функционал работает, дизайн — утилитарный.

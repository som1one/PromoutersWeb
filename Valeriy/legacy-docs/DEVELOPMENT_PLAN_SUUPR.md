# План разработки СУУПР

## 1. Цель плана

Этот документ фиксирует пошаговый план разработки MVP системы СУУПР: от проектирования до запуска первой рабочей версии. План ориентирован на быстрый выпуск релиза, который доказывает основной бизнес-процесс:

- назначение промоутера на маршрут;
- прохождение маршрута с геопозицией;
- сбор фотоотчётов;
- автоматический расчёт выплаты;
- контроль со стороны собственника и руководителя филиала.

## 2. Базовые допущения

- формат запуска: `MVP`;
- платформа: `web-приложение`;
- интерфейс промоутера: `mobile-first`;
- релизный горизонт: `3 спринта`;
- рекомендуемая длина спринта: `2 недели`;
- в MVP входят роли: `owner`, `branch_manager`, `ad_director`, `promoter`;
- роль `master` и блок заявок выводятся в post-MVP;
- уведомления в MVP допускаются в упрощённой реализации.

## 3. Командный контур

Для быстрой реализации MVP желательно закрыть следующие зоны ответственности:

- `Product / Analyst` — уточнение сценариев, приоритизация, приёмка;
- `Backend` — API, БД, роли, маршруты, выплаты, аудит;
- `Frontend` — кабинеты ролей, промоутерский интерфейс, формы отчётности;
- `QA` — сценарии проверки, smoke, регресс, мобильная проверка геопозиции;
- `DevOps` — окружения, деплой, хранение конфигов, мониторинг логов.

Если команда небольшая, роли `Product`, `QA` и `DevOps` могут быть совмещены частично, но ответственность по задачам должна оставаться явной.

## 4. Общая стратегия разработки

### Принцип 1. Сначала скелет системы

Сначала поднимается базовая архитектура: авторизация, роли, филиалы, пользователи, каркас UI, БД и инфраструктура.

### Принцип 2. Затем основной маршрут денег

После базы реализуется главный сценарий:

- директор по рекламе создаёт маршрут;
- промоутер получает маршрут;
- промоутер стартует выполнение;
- система собирает GPS и фото;
- промоутер завершает маршрут;
- система считает выплату.

### Принцип 3. Потом контроль и прозрачность

На завершающем этапе добавляются дашборды, уведомления, аудит и релизная стабилизация.

## 5. Этапы разработки

## Этап 1. Discovery и проектирование

### Цель

Убрать неопределённость до начала активной разработки.

### Задачи

- финализировать роли и границы MVP;
- утвердить список сущностей;
- описать пользовательские сценарии по ролям;
- описать API-контракты;
- согласовать модель выплат;
- определить правила хранения геопозиции и фото;
- зафиксировать, какие требования полного ТЗ переносятся в post-MVP.

### Артефакты на выходе

- утверждённое ТЗ;
- MVP scope;
- user flow по ролям;
- схема БД верхнего уровня;
- список API endpoint'ов;
- приоритетный backlog.

## Этап 2. Подготовка архитектуры и среды

### Цель

Подготовить основу, на которой можно безопасно развивать бизнес-логику.

### Задачи по backend

- создать backend-проект;
- подключить БД;
- настроить миграции;
- настроить конфиги по окружениям;
- настроить логирование;
- определить структуру модулей;
- реализовать базовую обработку ошибок;
- подготовить модель хранения файлов и фото.

### Задачи по frontend

- создать frontend-проект;
- настроить роутинг;
- настроить layout и guards;
- подготовить UI-kit или базовый набор компонентов;
- заложить mobile-first основу для кабинета промоутера.

### Задачи по DevOps

- настроить `dev`, `staging`, `production` окружения;
- настроить  переменные окружения;
- определить способ деплоя;
- подготовить базовую наблюдаемость: логи, ошибки, health-check.

### Артефакты на выходе

- рабочая локальная среда;
- staging-окружение;
- базовый каркас backend и frontend;
- миграционная схема;
- документ по окружениям и конфигам.

## Этап 3. Identity и управление доступом

### Цель

Открыть безопасный вход в систему и разграничить доступ по ролям и филиалам.

### Задачи

- реализовать вход по логину и паролю;
- реализовать получение текущего пользователя;
- реализовать роли `owner`, `branch_manager`, `ad_director`, `promoter`;
- реализовать привязку пользователя к филиалу;
- реализовать ограничения доступа по роли;
- реализовать ограничения доступа по филиалу;
- реализовать CRUD пользователей;
- реализовать CRUD филиалов;
- добавить аудит критичных действий по пользователям и ролям.

### Артефакты на выходе

- рабочая авторизация;
- управление пользователями;
- управление филиалами;
- ролевые ограничения;
- базовый audit log.

## Этап 4. Core business logic MVP

### Цель

Реализовать главный бизнес-сценарий работы промоутеров.

### Задачи по маршрутам

- создать сущность маршрута;
- создать точки маршрута;
- реализовать назначение маршрута промоутеру;
- реализовать статусы маршрута;
- реализовать просмотр маршрута по ролям.

### Задачи по выполнению маршрута

- реализовать старт маршрута;
- создать сессию выполнения маршрута;
- реализовать завершение маршрута;
- сохранить время начала и окончания;
- валидировать, что маршрут может завершить только назначенный промоутер.

### Задачи по геопозиции

- реализовать приём GPS-точек;
- хранить координаты с timestamp;
- различать точки старта, промежуточные точки и завершение;
- предусмотреть базовую защиту от пустых и некорректных координат.

### Задачи по фотоотчётам

- реализовать загрузку фото;
- связать фото с маршрутом и сессией;
- сохранять координаты и время съёмки;
- дать возможность просматривать фотоотчёты в интерфейсе руководящих ролей.

### Задачи по итоговому отчёту

- форма завершения маршрута;
- сохранение количества листовок;
- сохранение фактического времени;
- сбор итогового набора фотоотчётов;
- формирование краткого итогового отчёта по маршруту.

### Артефакты на выходе

- полный рабочий цикл маршрута;
- GPS-история;
- фотоотчётность;
- итоговый отчёт промоутера.

## Этап 5. Выплаты, уведомления и контроль

### Цель

Сделать MVP управляемым и финансово полезным.

### Задачи по выплатам

- реализовать типы оплаты: `hourly`, `per_leaflet`;
- реализовать ставки оплаты;
- реализовать расчёт суммы к выплате;
- сохранять расчёт как отдельную сущность;
- показывать детализацию по маршруту и промоутеру.

### Задачи по уведомлениям

- уведомление о назначении маршрута;
- напоминание промоутеру о фотоотчёте;
- уведомление о завершении маршрута руководителю;
- уведомление собственнику о ключевых изменениях.

### Задачи по контролю

- расширить audit log;
- журналировать создание маршрута;
- журналировать смену ставок;
- журналировать отправку и завершение отчёта;
- сделать базовый просмотр журнала действий.

### Артефакты на выходе

- автоматический расчёт выплат;
- базовые уведомления;
- прозрачный журнал критичных действий.

## Этап 6. Dashboards, QA и релиз

### Цель

Подготовить систему к использованию в реальной работе.

### Задачи по frontend

- кабинет собственника;
- кабинет руководителя филиала;
- кабинет директора по рекламе;
- кабинет промоутера;
- экраны списков, карточек, отчётов и выплат;
- адаптация под мобильные устройства для промоутера.

### Задачи по QA

- smoke-тесты по всем ролям;
- тесты на авторизацию;
- тесты на роли и доступы;
- тесты на маршруты;
- тесты на выплаты;
- проверка геопозиции на мобильных устройствах;
- проверка фотоотчётов;
- проверка сценариев уведомлений.

### Задачи по запуску

- наполнить тестовыми данными;
- провести UAT;
- исправить блокирующие дефекты;
- подготовить production-конфиги;
- выполнить релиз MVP.

### Артефакты на выходе

- готовая staging-версия;
- протестированный MVP;
- production-релиз;
- список post-MVP задач.

## 8. Зависимости и порядок реализации

Ниже зафиксированы ключевые зависимости:

- без auth и ролей нельзя начинать прикладные кабинеты;
- без сущностей `User`, `Branch` и `Route` нельзя реализовать маршрутный сценарий;
- без `PromoterSession` нельзя корректно считать время и выплаты;
- без геопозиции и фотоотчётов MVP теряет контрольную ценность;
- без audit log собственник не получает прозрачность управления;
- без staging и smoke-тестов выпуск MVP становится рискованным.

## 9. Definition of Done для MVP

MVP считается готовым, если выполнены все условия:

- авторизация работает стабильно;
- роли и филиальные ограничения соблюдаются;
- маршрут можно создать, назначить, запустить и завершить;
- геопозиция сохраняется при старте, в процессе и при завершении;
- фотоотчёты загружаются и доступны в просмотре;
- итоговый отчёт промоутера формируется и хранится;
- выплата рассчитывается автоматически;
- собственник и руководитель филиала видят базовый контрольный dashboard;
- ключевые действия пишутся в журнал;
- базовые уведомления работают;
- staging и production подготовлены;
- проведён smoke и регресс по критичным сценариям.

## 10. Основные риски проекта

- плавающая точность геопозиции на разных устройствах;
- ограничения браузеров на доступ к GPS и камере;
- задержки из-за неутверждённых бизнес-правил выплат;
- попытка включить в MVP блок мастеров и согласование расходов;
- рост объёма отчётности и аналитики раньше времени;
- недооценка mobile-first части для промоутера.

## 🔥 Файрвол (UFW)

### Что такое UFW?

**UFW (Uncomplicated Firewall)** — это упрощенный интерфейс для управления файрволом iptables в Linux. Он позволяет легко настраивать правила фильтрации сетевого трафика.

### Зачем нужен файрвол?

Файрвол защищает сервер от несанкционированного доступа, блокируя нежелательный трафик и разрешая только необходимые соединения.

### Правила, которые мы устанавливаем:

```bash
# Разрешаем SSH
sudo ufw allow 22/tcp

# Разрешаем порты для веб-интерфейсов
sudo ufw allow 8000/tcp  # Admin панель
sudo ufw allow 8001/tcp  # Dispatcher панель
sudo ufw allow 8002/tcp  # Master панель

# Включаем файрвол
sudo ufw enable
```

### Объяснение каждого правила:

#### 1. `sudo ufw allow 22/tcp` — SSH доступ

**Что делает:** Разрешает входящие подключения по порту 22 (стандартный порт SSH).

**Зачем:** Без этого правила вы не сможете подключиться к серверу по SSH после включения файрвола. Это критически важно для удаленного управления сервером.

**Почему TCP:** SSH использует протокол TCP для установления надежного соединения.

**⚠️ Важно:** Если вы используете нестандартный порт SSH (например, 2222), измените правило:
```bash
sudo ufw allow 2222/tcp
```

#### 2. `sudo ufw allow 8000/tcp` — Admin панель

**Что делает:** Разрешает доступ к административной панели на порту 8000.

**Зачем:** Это основной веб-интерфейс для управления системой. Доступен по адресу `http://your-server-ip:8000`.

**Кто использует:** Владельцы системы (роль `owner`), директора.

**Почему порт 8000:** Это стандартный порт для FastAPI приложений. Можно изменить в `docker-compose.yml`, но тогда нужно обновить правило файрвола.

#### 3. `sudo ufw allow 8001/tcp` — Dispatcher панель

**Что делает:** Разрешает доступ к панели диспетчера на порту 8001.

**Зачем:** Веб-интерфейс для диспетчеров, которые управляют заявками, назначают мастеров, отслеживают статусы.

**Кто использует:** Пользователи с ролью `dispatcher`.

**Почему отдельный порт:** Разделение интерфейсов по портам упрощает маршрутизацию и позволяет настроить разные уровни доступа через Nginx.

#### 4. `sudo ufw allow 8002/tcp` — Master панель

**Что делает:** Разрешает доступ к панели мастера на порту 8002.

**Зачем:** Веб-интерфейс для мастеров, где они видят свои заявки, обновляют статусы, загружают фото и документы.

**Кто использует:** Пользователи с ролью `master`.

**Почему отдельный порт:** Аналогично dispatcher — для разделения интерфейсов и упрощения настройки проксирования.

### Что НЕ разрешено файрволом?

По умолчанию UFW блокирует **все входящие соединения**, кроме явно разрешенных. Это означает:

- ❌ Порты базы данных (5432) — **не открыты наружу** (доступ только внутри Docker сети)
- ❌ Другие порты — заблокированы
- ✅ Только SSH и веб-интерфейсы — открыты

### Почему порт PostgreSQL не открыт?

```yaml
# В docker-compose.yml порт PostgreSQL закомментирован:
# ports:
#   - "5432:5432"
```

**Причина безопасности:** База данных должна быть доступна только внутри Docker сети, а не извне. Это защищает от:
- Прямых атак на базу данных
- Попыток подбора паролей
- Утечки данных при компрометации сервера

**Как работает:** Контейнеры `admin`, `bot`, `dispatcher`, `master` подключаются к PostgreSQL через внутреннее имя сервиса `postgres:5432`, которое резолвится внутри Docker сети.

## 🐳 Docker и Docker Compose

### Зачем использовать Docker?

1. **Изоляция:** Каждое приложение работает в своем контейнере, не влияя на другие
2. **Консистентность:** Одинаковая среда на всех серверах (dev, staging, production)
3. **Простота развертывания:** Один образ содержит весь код и зависимости
4. **Масштабируемость:** Легко добавить новые экземпляры сервисов

### Структура docker-compose.yml

```yaml
services:
  postgres:    # База данных
  bot:         # VK бот
  admin:       # Админ панель
  dispatcher:  # Панель диспетчера
  master:      # Панель мастера
```

### Почему все сервисы используют один образ?

```yaml
bot:
  image: greenteeea/vk-bot:latest
admin:
  image: greenteeea/vk-bot:latest
dispatcher:
  image: greenteeea/vk-bot:latest
master:
  image: greenteeea/vk-bot:latest
```

**Причина:** Весь код приложения находится в одном образе. Разные сервисы запускаются с разными командами:

- `bot` — запускает `vk_bot.py` (по умолчанию из `docker-entrypoint.sh`)
- `admin` — запускает `admin_fastapi.py`
- `dispatcher` — запускает `dispatcher_admin.py`
- `master` — запускает `master_admin.py`

**Преимущества:**
- Один образ для всех сервисов = проще обновление
- Меньше места на диске
- Единая версия кода во всех сервисах

### Volumes (тома данных)

```yaml
volumes:
  - ./data:/app/data
```

**Что делает:** Монтирует локальную директорию `./data` в контейнер по пути `/app/data`.

**Зачем:** 
- **БСО файлы** (`data/bso_files`) — сохраняются на хосте, не теряются при перезапуске
- **Чеки** (`data/receipts`) — аналогично
- **Персистентность:** Данные остаются на сервере даже при удалении контейнеров

**Почему `/app/data`:** Это стандартный путь внутри контейнера, где приложение ищет файлы.

## 📁 Структура директорий

### `/opt/servicebot` — корневая директория проекта

**Почему `/opt`:** 
- `/opt` предназначен для установки дополнительного программного обеспечения
- Это стандартное место для приложений, не входящих в базовую систему
- Легко найти и управлять

**Структура:**
```
/opt/servicebot/
├── docker-compose.yml    # Конфигурация Docker Compose
├── .env                  # Переменные окружения (секреты!)
├── data/                 # Данные приложения
│   ├── bso_files/        # Файлы БСО
│   └── receipts/         # Чеки
└── (остальное в Docker образе)
```

### Почему данные в `./data`, а не в контейнере?

**Проблема:** Если данные хранить внутри контейнера, они удалятся при:
- Пересоздании контейнера
- Обновлении образа
- Очистке Docker

**Решение:** Volume монтирует директорию хоста в контейнер, данные остаются на сервере.

## 🔐 Переменные окружения

### Файл `.env`

**Что это:** Файл с секретными данными и настройками приложения.

**Почему отдельный файл:**
- Не попадает в Git (должен быть в `.gitignore`)
- Легко менять без пересборки образа
- Разные настройки для разных серверов

### Важные переменные:

#### `VK_BOT_TOKEN`
**Что:** Токен для доступа к VK API бота.

**Зачем:** Без токена бот не сможет отправлять сообщения и обрабатывать команды.

**Безопасность:** ⚠️ **НИКОГДА** не коммитьте в Git! Это секретный ключ.

#### `ADMIN_IDS`
**Что:** Список ID пользователей, которые автоматически получают роль `owner`.

**Формат:** `1080026562` или `1080026562,123456789` (через запятую)

**Зачем:** При первом входе пользователь из этого списка автоматически становится владельцем системы.

**Как работает:** Код проверяет `ADMIN_IDS` при создании/обновлении пользователя и назначает роль `owner`.

#### `DATABASE_URL`
**Что:** Строка подключения к базе данных.

**Формат:** `postgresql+psycopg2://user:password@host:port/database`

**Почему в docker-compose.yml переопределяется:**
```yaml
environment:
  DATABASE_URL: postgresql+psycopg2://serviceuser:servicepass@postgres:5432/servicebot
```

**Причина:** В Docker сети сервис PostgreSQL доступен по имени `postgres`, а не `localhost`. Это имя резолвится Docker'ом автоматически.

#### `VK_GROUP_ID`
**Что:** ID группы VK, к которой привязан бот.

**Зачем:** Используется для настройки Long Poll API (если используется).

## 🌐 Порты и сервисы

### Схема портов:

```
Внешний мир → Файрвол → Docker → Контейнеры
     ↓            ↓         ↓          ↓
  8000-8002    Разрешены  Маршрутизация  FastAPI
```

### Почему порты 8000, 8001, 8002?

1. **8000** — стандартный порт для FastAPI/uvicorn
2. **8001, 8002** — следующие порты для других сервисов
3. **Не используем 80/443** — эти порты обычно заняты Nginx (если настроен)

### Альтернатива: Nginx как reverse proxy

Если у вас есть домен, лучше настроить Nginx:

```nginx
server {
    listen 80;
    server_name your-domain.com;
    
    location / {
        proxy_pass http://localhost:8000;  # Admin
    }
    
    location /dispatcher {
        proxy_pass http://localhost:8001;  # Dispatcher
    }
    
    location /master {
        proxy_pass http://localhost:8002;  # Master
    }
}
```

**Преимущества:**
- Один порт (80/443) вместо трех
- SSL сертификаты (Let's Encrypt)
- Красивые URL (`your-domain.com` вместо `ip:8000`)
- Дополнительная защита (rate limiting, блокировка ботов)

**Тогда файрвол:**
```bash
sudo ufw allow 80/tcp   # HTTP
sudo ufw allow 443/tcp  # HTTPS
# Порты 8000-8002 можно закрыть (доступ только через Nginx)
```

## 🛡️ Безопасность

### Принципы безопасности, которые мы применяем:

#### 1. Минимальные привилегии

**Что:** Каждый сервис имеет доступ только к тому, что ему нужно.

**Как:**
- PostgreSQL доступен только внутри Docker сети
- Каждый контейнер изолирован
- Пользователь в контейнере не root (если настроено)

#### 2. Файрвол блокирует все по умолчанию

**Принцип:** "Deny by default, allow explicitly"

**Что это значит:** Всё заблокировано, кроме явно разрешенного.

**Почему:** Если забыли открыть порт — лучше недоступность, чем уязвимость.

#### 3. Секреты в переменных окружения

**Что:** Токены и пароли хранятся в `.env`, не в коде.

**Почему:**
- Код можно публиковать в Git без страха утечки
- Легко менять секреты без пересборки
- Разные секреты для разных окружений

#### 4. База данных не доступна извне

**Что:** Порт 5432 не пробрасывается наружу.

**Почему:** Защита от прямых атак на базу данных.

**Как подключиться при необходимости:**
```bash
# Только с сервера или через SSH туннель
docker compose exec postgres psql -U serviceuser -d servicebot
```

#### 5. Регулярные обновления

**Что:** Обновляем Docker образы регулярно.

**Почему:** Исправления безопасности, новые функции.

**Как:**
```bash
docker compose pull
docker compose up -d
```

## 📊 Сводная таблица правил

| Правило | Порт | Протокол | Назначение | Кто использует |
|--------|------|----------|------------|----------------|
| SSH | 22 | TCP | Удаленное управление | Администратор |
| Admin | 8000 | TCP | Админ панель | Owner, Director |
| Dispatcher | 8001 | TCP | Панель диспетчера | Dispatcher |
| Master | 8002 | TCP | Панель мастера | Master |
| PostgreSQL | 5432 | TCP | База данных | **Только внутри Docker** |

## 🔄 Типичные сценарии

### Сценарий 1: Нужно открыть доступ только с определенного IP

```bash
# Разрешить SSH только с офисного IP
sudo ufw allow from 192.168.1.100 to any port 22

# Разрешить веб-интерфейсы только с определенного IP
sudo ufw allow from 192.168.1.100 to any port 8000
sudo ufw allow from 192.168.1.100 to any port 8001
sudo ufw allow from 192.168.1.100 to any port 8002
```

### Сценарий 2: Изменить порты веб-интерфейсов

1. Изменить в `docker-compose.yml`:
```yaml
admin:
  ports:
    - "9000:8000"  # Внешний:Внутренний
```

2. Обновить файрвол:
```bash
sudo ufw delete allow 8000/tcp
sudo ufw allow 9000/tcp
```

3. Перезапустить:
```bash
docker compose up -d
```

### Сценарий 3: Настроить Nginx с SSL

1. Установить Nginx и Certbot
2. Настроить конфигурацию (см. DEPLOYMENT_GUIDE.md)
3. Обновить файрвол:
```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
# Опционально: закрыть 8000-8002
sudo ufw delete allow 8000/tcp
sudo ufw delete allow 8001/tcp
sudo ufw delete allow 8002/tcp
```

# Перенос PJ2-функциональности в Jinja-админку и доведение до ТЗ

## Введение

В системе СУУПР сейчас две UI-поверхности:

1. **`/admin/*`** — серверная Jinja-админка (FastAPI + Jinja2), таблицы и формы. **Это основной интерфейс по решению заказчика.** Сюда переносим всё.
2. **`/`** — React/Vite SPA, мобильный кабинет промоутера и мастера. **Не трогаем в этой работе.** Промоутер использует SPA для GPS/камеры, остальные роли — Jinja-админку.

Основной источник логики, которую переносим: legacy-проект `Valeriy/PythonProject2/` (PJ2). Большая часть его моделей и услуг уже портирована: миграция `0006_merge_pj2_tables.py` свела таблицы (cities, equipment_types, orders, stats, attendance, penalties, system_settings) в общую БД, в `services/` есть порт `commission`, `equipment_types`, `statistics`, `cash`, `sd`, `cities`, `orders`. Не хватает целостного UI и нескольких сценариев из ТЗ.

## Принципы

- **Серверный рендер на Jinja**, минимум JS в админке (только Leaflet на маршрутных страницах + точечный fetch для AJAX-действий типа «отметить уведомление прочитанным»).
- **Mobile-first адаптив** — каждая страница должна быть пригодна на 360px ширине (промоутерский Android), без горизонтального скролла, без обрезки кнопок.
- **CI как единственный канал доставки.** Каждая волна = ветка/коммит → push → GitHub Actions deploy → smoke-сценарий в логе.
- **Smoke-сценарий обязателен на каждую волну.** В CI после деплоя — серия `curl`-запросов с куками, эмулирующих ключевой пользовательский путь. Если smoke не зелёный — волна не считается готовой.
- **Без UI «вокруг» SPA.** SPA не правится, на него только ссылка из админки если нужно (например, мобильный URL для промоутера).

## Глоссарий

- **W0..WN** — волны работы.
- **Smoke-сценарий** — последовательность HTTP-запросов в CI (curl с cookie jar), которая валидирует ключевой путь после деплоя. Не заменяет ручной приёмки, но ловит регрессии.
- **PJ2** — `Valeriy/PythonProject2/`, legacy-источник.

## Требования по волнам

Каждая волна — отдельный коммит/PR в `main`, со своим smoke-сценарием в CI. Условие приёмки: smoke зелёный + ручная проверка по чеклисту волны.

### W0 — Срочные фиксы (блокеры)

**Цель:** убрать то, что мешает заказчику смотреть админку прямо сейчас.

#### Требование W0.1 — починить редирект после `/admin/login`

**Пользовательская история:** Как owner.demo, я хочу залогиниться через `http://72.56.38.35/admin/login` и попасть в админку, а не вернуться обратно на форму логина.

**Корневая причина:** `set_auth_cookies` ставит `secure = not settings.debug` → на проде `APP_DEBUG=false` → `secure=True`. Браузер не отдаёт Secure-cookie на http-соединении → следующий запрос приходит без `access_token` → `WebAuthException` → редирект.

#### Критерии приёмки

1. КОГДА в `Settings` появляется поле `web_cookie_secure: bool = True`, ТОГДА его значение читается из ENV `WEB_COOKIE_SECURE`.
2. КОГДА `set_auth_cookies` ставит cookies, ТОГДА флаг `secure` берётся из `settings.web_cookie_secure`, а НЕ из `not settings.debug`.
3. КОГДА в проде в `.env` задано `WEB_COOKIE_SECURE=false`, ТОГДА после успешного `POST /admin/login` куки сохраняются и `GET /admin/` возвращает 200 (не редирект на login).
4. КОГДА появится HTTPS, ТОГДА переключение на `WEB_COOKIE_SECURE=true` не потребует правок кода.
5. КОГДА запускается smoke-сценарий W0 в CI, ТОГДА он логинит owner.demo через curl и получает 200 на `/admin/`. Если редирект → smoke красный.

#### Требование W0.2 — починить 500 на статистике и дашборде

**Пользовательская история:** Как owner.demo, я хочу открыть `/admin/` и `/admin/stats` без 500.

#### Критерии приёмки

1. КОГДА owner.demo заходит на `/admin/`, ТОГДА сервер отвечает 200, страница рендерится без traceback.
2. КОГДА owner.demo заходит на `/admin/stats`, ТОГДА сервер отвечает 200.
3. ЕСЛИ запросы к статистике падают на отсутствующих PJ2-таблицах или несошедшихся данных, ТО возвращается понятный pyplaceholder («нет данных за период»), не 500.
4. КОГДА smoke W0 проходит, ТОГДА в логах CI есть `curl /admin/=200` и `curl /admin/stats=200`.

### W1 — Адаптивный CSS (сквозной)

**Пользовательская история:** Как руководитель филиала с телефона на 360px, я хочу пользоваться админкой без горизонтального скролла и с тач-таргетами ≥44px.

#### Критерии приёмки

1. КОГДА страница рендерится на 360×640, ТОГДА горизонтальный скролл отсутствует.
2. КОГДА элементы управления (`<button>`, ссылки навигации, чекбоксы строк), ТОГДА их минимальный hit-area = 44×44px.
3. КОГДА таблицы с >5 колонок открываются на ≤768px, ТОГДА они либо скроллятся внутри своего контейнера (`overflow-x:auto`), либо превращаются в карточки (адаптивная подача строки).
4. КОГДА в шапке `base.html` отображается навигация, ТОГДА на ≤768px она сворачивается в гамбургер-меню или нижнюю панель.
5. КОГДА smoke W1 проходит, ТОГДА в CI запускается lighthouse-mobile (или альтернатива) и получает ≥80 по критерию «mobile usability» (если нереально автоматизировать — заменить на ручной чеклист в `docs/`).

### W2 — Управление пользователями и ролями (owner)

**Пользовательская история:** Как owner, я хочу создавать/редактировать пользователей, менять им роль и филиал, и видеть аудит этих действий.

#### Критерии приёмки

1. КОГДА owner открывает `/admin/users`, ТОГДА он видит список с фильтром по роли и филиалу.
2. КОГДА owner редактирует пользователя, ТОГДА доступны поля: ФИО, телефон, email, роль, филиал, статус.
3. КОГДА owner меняет роль или филиал пользователя, ТОГДА в `audit_log` пишется запись с прежним и новым значениями.
4. КОГДА non-owner пытается зайти на `/admin/users`, ТОГДА получает 403 (Forbidden шаблон).
5. Smoke W2: логин owner → создать пользователя через POST → найти его в списке → удалить → не виден в списке.

### W3 — Статистика и директор по рекламе

**Пользовательская история:** Как руководитель филиала, я хочу видеть средний чек, оборот филиала и ЗП мастеров по направлениям. Как директор по рекламе, я хочу видеть «своих» промоутеров и назначать им маршруты.

#### Критерии приёмки

1. КОГДА руководитель филиала открывает `/admin/stats`, ТОГДА он видит за последние 30 дней: средний чек, оборот по филиалу, ЗП мастеров по направлениям (Equipment type → сумма выплат мастерам).
2. КОГДА филиал не его — данные не показываются (cross-branch isolation).
3. КОГДА директор по рекламе открывает `/admin/masters` или дочерний раздел «Мои промоутеры», ТОГДА видит только промоутеров, назначенных на его маршруты.
4. КОГДА директор открывает страницу маршрута, ТОГДА может назначить/снять промоутера.
5. Smoke W3: логин director.center → GET /admin/stats=200 → проверка что в HTML встречается `data-stat="branch-revenue"`.

### W4 — План расходов и согласование

**Пользовательская история:** Как руководитель филиала, я хочу составить план расходов (статьи + суммы) и отправить на согласование собственнику. Как owner, я хочу одобрять/отклонять с комментарием. Каждый шаг → уведомление и аудит.

#### Критерии приёмки

1. КОГДА руководитель филиала открывает `/admin/expense-plans/create`, ТОГДА видит форму с динамическими строками (название/категория/количество/цена/сумма).
2. КОГДА план сохранён в статусе DRAFT, ТОГДА руководитель может его редактировать; в SUBMITTED — нет.
3. КОГДА план переходит в SUBMITTED, ТОГДА owner получает запись в `notifications`.
4. КОГДА owner открывает план в SUBMITTED, ТОГДА видит кнопки «Одобрить» и «Отклонить с комментарием».
5. КОГДА owner одобряет/отклоняет, ТОГДА в `audit_log` запись + статус плана меняется + руководитель получает уведомление.
6. КОГДА non-owner и non-creator пытаются открыть план — 403.
7. Smoke W4: manager.center создаёт план → submits → owner.demo видит уведомление → approves → manager.center видит approved.

### W5 — Создание маршрутов и Leaflet-редактор

**Пользовательская история:** Как директор по рекламе, я хочу создать маршрут с точками на карте, прикрепить промоутера и ставку. Как промоутер — увидеть свой маршрут в SPA и стартовать.

#### Критерии приёмки

1. КОГДА директор открывает `/admin/routes/create`, ТОГДА видит форму: название, описание, дата, филиал, промоутер, ставка, и **карту Leaflet** для расстановки точек (старт, чекпоинты, финиш).
2. КОГДА точки расставлены и форма сабмитится, ТОГДА создаётся `Route` + `RoutePoint[]`, статус DRAFT.
3. КОГДА маршрут переходит в ASSIGNED (через UI), ТОГДА промоутер получает уведомление.
4. КОГДА директор смотрит существующий маршрут, ТОГДА видит карту с точками + GPS-треки промоутера (если сессия активна/завершена).
5. КОГДА owner смотрит маршрут другого филиала — отказ доступа.
6. Smoke W5: director.center открывает /admin/routes/create → 200 → POST с точками → созданный route получает id → его id есть в списке /admin/routes/.

### W6 — Заявки мастеру (CRUD + статусы + БСО)

**Пользовательская история:** Как мастер, я хочу принимать заявку, переключать статусы и прикреплять БСО. Как директор/руководитель — видеть статус заявки и геопозицию мастера.

#### Критерии приёмки

1. КОГДА мастер открывает `/admin/master-requests/{id}`, ТОГДА видит кнопки переходов: NEW→ACCEPTED→ON_THE_WAY→IN_PROGRESS→COMPLETED→HANDED_OVER.
2. КОГДА мастер делает переход через скип (например NEW→IN_PROGRESS), ТОГДА получает 422.
3. КОГДА мастер на статусе HANDED_OVER, ТОГДА доступна форма прикрепления БСО (file upload).
4. КОГДА мастер добавляет комментарий, ТОГДА он появляется в детальной странице заявки и в аудите.
5. КОГДА статус ON_THE_WAY/IN_PROGRESS, ТОГДА в детали отображается «GPS активен» (значок + время последнего пинга).
6. Smoke W6: master.center логинится → берёт NEW заявку → переходит accepted→on_the_way → /admin/master-requests/{id}=200 → статус виден → переходит handed_over → закрывается.

### W7 — Выплаты и финотчёт с гиперссылками

**Пользовательская история:** Как owner, я хочу видеть итоговые выплаты по промоутерам со статусами (рассчитан/одобрен/выплачен) и переходить из строки финотчёта на детализацию по промоутеру.

#### Критерии приёмки

1. КОГДА открыта `/admin/payouts/`, ТОГДА таблица: промоутер, маршрут, тип оплаты, единицы, сумма, статус, кнопка действия.
2. КОГДА owner нажимает «Одобрить» на статусе CALCULATED, ТОГДА выплата → APPROVED + аудит + уведомление промоутеру.
3. КОГДА owner нажимает «Отметить выплаченным» на APPROVED, ТОГДА выплата → PAID + дата.
4. КОГДА в `/admin/cash` есть строка по промоутеру, ТОГДА имя промоутера — гиперссылка на `/admin/payouts/?promoter_id={id}`.
5. КОГДА запрашивается CSV-экспорт `/admin/payouts.csv?from=...&to=...`, ТОГДА скачивается файл с правильным заголовком и кодировкой UTF-8 BOM.
6. Smoke W7: owner.demo видит payouts → меняет статус calculated→approved → видит изменение в БД через повторный GET.

### W8 — Уведомления (реальные события)

**Пользовательская история:** Как owner, я хочу получать уведомления о действиях руководителя филиала и других значимых событиях. Видеть бейдж непрочитанного в шапке.

#### Критерии приёмки

1. КОГДА в системе происходит одно из событий: создание/изменение пользователя, перевод плана расходов в SUBMITTED/APPROVED/REJECTED, создание/изменение маршрута, переход статуса заявки мастера, ТОГДА в `notifications` создаётся запись для owner-а (а для целевых событий — для соответствующего получателя).
2. КОГДА owner открывает `/admin/`, ТОГДА в шапке отображается бейдж с числом непрочитанных уведомлений.
3. КОГДА owner кликает по уведомлению, ТОГДА открывается детальная страница (или связанная сущность), запись помечается как READ, бейдж уменьшается.
4. Smoke W8: manager.center делает действие → owner.demo получает unread=N+1 → читает → unread=N.

### W9 — Сверка с ТЗ и финальное smoke-кольцо

**Пользовательская история:** Я хочу пройти end-to-end сценарий ТЗ: заказчик создаёт пользователей, маршрут, мастер закрывает заявку, промоутер сдаёт фотоотчёт (через API/SPA), выплата рассчитывается, owner одобряет.

#### Критерии приёмки

1. Smoke W9 в CI проходит полный цикл из 8+ шагов с разными ролями, проверяя что после каждого шага БД и UI находятся в ожидаемом состоянии.
2. Создан документ `docs/UAT_CHECKLIST.md` (обновить существующий) с пошаговыми инструкциями для ручной приёмки заказчиком.
3. Создан документ `docs/TESTING_GUIDE.md` (обновить) с описанием smoke-каркаса и как его запускать локально.

## Сквозные требования

### Логирование и диагностика

1. КОГДА в `/admin/*` происходит exception, ТОГДА в логах есть полный traceback (а не «500» без причины), и uvicorn логирует на уровне INFO ключевые действия (login success/fail, role change, payout state change).
2. КОГДА в CI запускается deploy, ТОГДА последний шаг smoke прогоняет минимум 3 пользовательских сценария (owner login → menu, manager → expense plan, master → request status) и при failure возвращает 1.

### Сидер демо-данных

1. КОГДА запускается `scripts/seed_demo_data.py`, ТОГДА все демо-аккаунты восстанавливаются с одинаковым паролем `demo12345`, идемпотентно (повторный запуск не дублирует записи).
2. Сидер дополняется так, чтобы каждая волна имела готовые сценарии для smoke (есть план в SUBMITTED, есть маршрут в IN_PROGRESS, есть заявка в каждом статусе).

### Обратная совместимость

1. SPA на `/` НЕ ДОЛЖНО ломаться от изменений в Jinja-админке.
2. API `/api/v1/*` НЕ ДОЛЖНО менять контракт без необходимости (если меняется — обновляются типы во фронте SPA).

## Что НЕ делаем в рамках этой работы

- Не трогаем мобильный SPA (`/`).
- Не пишем новый дизайн-систему — расширяем существующий `admin.css`.
- Не делаем HTTPS / Let's Encrypt — это отдельная задача.
- Не интегрируем реальный SMS-провайдер — оставляем заглушку.
- Не делаем PWA / push-уведомления — только in-app notifications.
